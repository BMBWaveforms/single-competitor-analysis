# 证据与体验约定

## 证据区分

- **实测事实**：在注明的产品、版本、账号、设备、地区和场景下亲自观察到的行为。一次体验只支持对应场景，不代表全站表现。
- **公开资料**：官方说明、公开规则或其他可追溯来源。标明来源和日期；宣传表述不等于实际效果或后台实现。
- **研究推断**：说明依据、成立条件和可行的替代解释。用户可见行为不能单独证明后台架构。
- **未知/受限**：说明缺少什么证据、为何无法验证，以及它是否会影响当前判断。未发现不等于不存在。

影响关键判断的证据需可回查到来源、位置和日期/版本。不同来源互相转载不算独立印证。涉及用户隐私时，只保留研究所需信息。

## 委托用户体验

在用户需要亲自操作时，说明足以让其完成任务的最少信息：

- 要回答的问题，以及这项体验对研究判断的作用。
- 可复现的操作步骤、建议输入和要注意的产品反馈。
- 需要保存的内容，例如结果文本、截图、异常现象或修改/重试过程。
- 完成后回传的内容；允许用户直接用自然语言描述，不要求填写大表。

确认用户的体验条件（如版本、设备、账号或地区）和操作范围。区分用户亲历与转述材料；用户的个人偏好有价值，但不直接当成普遍用户结论。未经授权不要求购买、联系他人或执行有外部影响的操作。

## Agent 分析边界

在单竞品研究中，只在观察到 Agent 行为、公开材料支持，或研究目标明确关注 Agent 时调用 `single-agent-analysis`。传入准确对象、场景、原始输入输出、操作记录和已知资料；调用结果作为技术层证据之一，不把反推的提示词、工具或状态结构写成产品真实后台配置。

多 Agent 关系只有证据支持时才描述为事实。先分析整体可见协作，再对关键 Agent 按需深入；不要仅凭职业角色、页面模块或一次工具调用断言 Agent 数量。
