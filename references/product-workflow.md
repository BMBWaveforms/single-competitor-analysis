# 研究流程与层间讨论

## 研究方式

研究围绕一个产品和一个明确任务展开。先确定研究要帮助理解或判断什么，再体验产品、记录证据；遇到疑点时补查公开资料或设计补测。不要把完成模板当成研究完成，也不要把单竞品观察推成市场共识。

五层是检视产品的研究视角，不是刚性章节，也不要求同样深度。结合研究目标决定先后和投入；如果新证据要求回看前一层，说明原因并与用户讨论。

## 每层的工作节奏

1. 在本层内收集与判断相关的材料和体验证据，记录未覆盖的问题。
2. 形成阶段性判断，并区分观察事实、来源陈述和解释性推断。
3. 暂停向用户简要汇报本层关键发现、重要依据和不确定之处，提出下一层的研究建议及理由。
4. 等用户讨论、修正或决定重点后，再继续下一层。

阶段交流只呈现对判断有影响的信息，不复制研究日志或详尽证据表。证据明细留给研究交接材料。层内出现可能改变研究方向的重要新发现时，可以及时打断交流；一般操作不逐项询问。

## 五层分别回答的问题

### 定位

产品服务谁、在什么场景解决什么问题、替代何种现有做法、通过什么机制交付价值？区分官方表述和研究归纳。商业模式仅在会影响本次判断时分析。

### 用户

用户如何完成一个核心任务？从入口、输入、操作、产品反馈、结果到后续行动，分别发生了什么？异常时如何恢复？产品交付的结果有多大程度可直接使用，还需要哪些产品外处理？

体验前明确用户任务、输入、预期和可观察标准。标准研究通常覆盖一条核心任务路径及至少两个相关异常或恢复情形，具体覆盖由目标和访问条件决定。至少保留有代表性的实际输出或可核验记录；不编造访谈、情绪或失败情节。

### 技术

可观察行为更符合固定流程、单 Agent、多 Agent、混合方式中的哪种？哪些部分有直接证据，哪些只能推断？如果多 Agent，分析可见的任务分配、上下文传递、结果汇总、确认、冲突处理与恢复。

只在技术机制与研究目标相关时深入。网页功能或角色名称本身不能证明 Agent 数量；架构未知时保留未知。需要逐个分析 Agent 时，读取并按需调用 `single-agent-analysis`，把已有输入、输出和证据传过去，避免重复体验。

### 模型

公开或可核验信息能说明哪些任务使用何种模型？选择原因和替换限制是否有证据？未知时写明缺口，不以回答风格、速度或产品支持的助手品牌推断实际模型。

### 基础

产品依赖哪些内容、数据或供给？由谁或什么机制生产、核实、更新、复用和分发？研究需要时，再分析成本驱动、收费和可累积资产。没有直接依据时不推断实际经营数字、留存或壁垒。

## 从发现到可借鉴判断

把重要机制讲清楚：产品如何做、对应什么用户问题、为什么可能有效、成立需要什么条件、哪些部分不宜照搬、还需要什么验证。呈现反证和替代解释；单一产品的优点不证明用户需求，也不证明己方应该采用。

研究的分析深度由问题和证据决定。保留能改变解释或迁移判断的细节；删除与判断无关的细枝末节。不要为每层强行造结论或把未知填成完整故事。
